# M6 -- the final evaluation: XIVO vs OpenVINS on EuRoC MAV, stereo + IMU

Milestone M6 of `notes-n-prompts/plan-euroc.md`. Measured on branch
`auto-eurocfps` at `3cbbdfb`, against the OpenVINS baseline from M1.

This milestone adds no tuning. It exists to answer the brief's question -- how does
XIVO compare to OpenVINS on EuRoC, in accuracy and in throughput, with **one
configuration for all eleven sequences** -- at an ensemble size large enough that
the answer does not move when you look again.

**The short answer.** In stereo + IMU, over eleven sequences, XIVO and OpenVINS
are close on the aggregate and *completely different* per sequence. XIVO wins the
five Machine Hall sequences by 37% and loses the six Vicon Room sequences by 42%;
the near-tie in the eleven-sequence mean is those two effects cancelling. XIVO wins
3 of the 5 accuracy metrics (both orientation metrics and RPE-8 position, all at
> 4 sigma), ties `ate_002` at the accurate operating point, loses ATE position, and
runs 8.0% slower end-to-end at the shipped operating point.

**The methodological finding, which cost this milestone its first day.** M5's
accuracy screens were n=3 jitter ensembles. That is too few on EuRoC: re-running
*the identical shipped configuration* at n=6 and n=10 -- with members 0-2
bit-identical to M5's -- moved the eleven-sequence `ate_002` mean 0.098 -> 0.102 ->
0.103. Every relative claim in M5 §4 and §9.2 inherits that error, and M5 has been
corrected. The rule going forward is **screen at n=3, ship at n=10** (§1.2).


## 1. What is being compared

### 1.1 One configuration each, and what that means here

| | XIVO | OpenVINS |
| --- | --- | --- |
| version | `auto-eurocfps` @ `3cbbdfb` | v2.7 (M1 baseline) |
| config | `cfg/euroc_stereo.json`, generated by `scripts/make_euroc_cfg.py` from the dataset's own `sensor.yaml` | shipped `euroc_mav` estimator config |
| per-sequence tuning | none | none |
| deviations from shipped defaults | the M2-M5 tuning, all in the generator | `--init_dyn_use 1` on every sequence |
| what varies across ensemble members | `X.Vsb` + k*1e-6 m/s | `--gravity_mag` |

Both sides are genuinely one configuration for all eleven. The single OpenVINS
deviation, `--init_dyn_use 1`, is not a tuning knob but a fix: with the shipped
static-only initializer OpenVINS diverges on `MH_04_difficult` in 6 of 6 members,
because that sequence opens with a take-off rather than a stationary period.
Applying it uniformly to all sequences and all members keeps the "one
configuration" property intact (M1 notes, `ov_euroc_ens.sh:11`).

Two XIVO operating points are reported, because M5's front-end work produced a
genuine Pareto pair and the choice between them is a real decision rather than an
oversight:

| | | ms/frame | what it is |
| --- | --- | --- | --- |
| **`fast`** | shipped | 11.593 | `histogram_method NONE`, `FAST.threshold 7`, `KLT.max_level 2`, `fast_png_decode false` |
| **`acc`** | alternative | 13.921 | the same, with CLAHE restored and `FAST.threshold` back to 20 |

`acc` is reachable in two flags
(`make_euroc_cfg.py --histogram_method CLAHE --fast_threshold 20`). §5 gives the
reasons `fast` is the one that ships.

### 1.2 Ensembles: n=10, and the n=3 mistake it corrects

XIVO's per-run output is deterministic, so an "ensemble" here perturbs the initial
body velocity by k*1e-6 m/s -- a perturbation far below any physical uncertainty,
whose only purpose is to sample the chaotic sensitivity of the gating decisions
downstream. On EuRoC that sensitivity is large: `V2_03_difficult` spans
0.168-0.316 m of `ate_002` across ten such members.

M5 screened at n=3. The evidence that this was too few is direct rather than
statistical:

| | members | `ate_002`, all 11 |
| --- | --- | --- |
| `results/euroc_fps_ship` | 0,1,2 | 0.098 |
| `results/euroc_m6_xivo` | 0-5 | 0.102 |
| `results/euroc_m6_final/fast` | 0-9 | **0.103** |

These are the same configuration and the same members -- runs r0-r2 of the n=6 and
n=10 passes are bit-identical to the n=3 pass, checked value by value. Members 3-5
simply happened to be worse, mostly on `V2_03_difficult` (0.228 / 0.316 / 0.213
against the first three members' 0.187 / 0.202 / 0.168) and one 0.124 outlier on
`MH_01_easy`. Nothing about the estimator changed; only the size of the sample did.

At n=10 the standard error of the eleven-sequence mean is 0.0016 m for `fast` and
0.0009 for `acc`. That is small enough to resolve the differences this milestone
has to report, and it is why every number below is n=10 (XIVO, 110 stereo runs per
arm) or n=6 (OpenVINS, 66 stereo runs; its ensemble is nearly deterministic --
several sequences show +-0.000 -- so its SE is 0.0006 at n=6 and more members would
buy nothing).

**A caveat these error bars do not cover.** They are the reproducibility of *one
configuration's* ensemble mean. They are not the uncertainty in "XIVO's accuracy"
as a design: perturbing a neutral configuration knob moves the mean roughly six
times as far as reseeding does, which is a separate and larger source of variance
already recorded for this codebase. A 0.001 m difference between two *different
configurations* is not meaningful even when both have 0.0009 error bars.

### 1.3 Metrics

Five, on every run, all lower-is-better:

* **`ate_002`** -- `evaluate_ate.py` with `--max_difference 0.02`, i.e. a 0.02 s
  association window. Sim(3)-free but computed after a similarity alignment that is
  **blind to a global rotation**, so it does not charge a constant tilt.
* **`ov ATE pos` / `ov ATE ori`** -- `ov_eval error_singlerun posyaw`. `posyaw`
  aligns position and yaw only, so roll and pitch error is charged in full. About
  0.31 deg of the orientation figure is the benchmark's own floor.
* **`RPE8 pos` / `RPE8 ori`** -- the same tool's 8 m relative pose error. This is
  the drift-rate metric; it is insensitive to a single early excursion in a way
  that ATE is not, which matters here (§3).

Throughput and memory are measured separately, under the one-core protocol
(§2.2), never from the accuracy pass -- under the accuracy pass's 220-way
oversubscription the same configuration reads anywhere from 27.9 to 65.7 FPS.

| --- | --- | --- |

So: **XIVO wins both orientation metrics and the position drift rate; OpenVINS

Counting the 55 per-sequence-per-metric cells three ways, XIVO takes 32 of them
(`acc` 17, `fast` 15) against OpenVINS' 23.

### 2.2 Throughput and memory

One core, ASLR off, all thread pools at 1, sequences serial, `-mode runOnly`
(no scoring, no per-frame dump), all eleven sequences, frame-weighted total wall
over total frames. Protocol reproducibility is sd 0.002 ms.

| | ms/frame | FPS | peak RSS | vs OpenVINS |
| --- | --- | --- | --- | --- |
| XIVO M4 (pre-M5) | 14.756 | 67.8 | 95.3 MB | +37.4% |
| XIVO `acc` | 13.921 +- 0.000 | 71.8 | 96.2 MB | +29.7% |
| **XIVO `fast`** (shipped) | **11.593** | **86.3** | 97.1 MB | **+8.0%** |
| OpenVINS | 10.737 | 93.1 | 99.2 MB | -- |

XIVO `fast` is **8.0% slower end-to-end** and its peak RSS is **3.0 MB lower**
than OpenVINS'. `acc` is 29.7% slower -- it gives back 2.328 of M5's 3.163 ms.

The `+- 0.000` on `acc` is two repeats measuring 13.9207 and 13.9210 ms/frame.
That is the protocol working as specified in §1.3 and is why one repeat is enough
for the others.

Two things about these numbers are easy to get wrong.

**The RSS figure depends on the mode, and only `runOnly` is the deployment
figure.** Under `-mode eval` -- which writes a per-frame dump for scoring -- XIVO's
peak RSS is 131.3 MB against OpenVINS' 105.1 MB. That +34 MB is the dump buffer,
not the estimator; OpenVINS' equivalent overhead is +6 MB. Quoting the eval-mode
number would report a 25% memory *deficit* where the deployment configuration has a
2% advantage.

**End-to-end favours XIVO more than the estimator alone does.** XIVO's PNG decode
is faster than OpenVINS' `imread` (2.972 vs 3.197 ms/frame over all eleven, M5
§8.1), which masks part of the estimator gap:

| | end-to-end | decode | estimator only |
| --- | --- | --- | --- |
| XIVO `acc` | 13.921 | 2.972 | 10.949 (+45.2%) |
| XIVO `fast` | 11.593 | 2.972 | 8.621 (**+14.3%**) |
| OpenVINS | 10.737 | 3.197 | 7.542 |
| `fast` vs OV | +8.0% | -7.0% | **+14.3%** |

The honest framing is the estimator column: **XIVO's estimator is 14% more
expensive**, and M5 §8.1/§9.3 localises essentially all of it to the covariance
update over a deliberately larger state -- 90 in-state features and a 20-pose OOS
window against OpenVINS' 50 SLAM features and 11 clones -- not to unoptimised code.
`actual-update` measured 3.65 +- 0.04 ms and was invariant under every front-end
knob screened in M5.


## 3. The result the aggregate hides: Machine Hall vs Vicon Room

This is the most substantive finding of the comparison, and it is invisible in any
eleven-sequence mean. `ate_002`, split by environment:

| | XIVO `acc` | XIVO `fast` | OpenVINS |
| --- | --- | --- | --- |
| Machine Hall (5 seqs) | **0.0848** | 0.0883 | 0.1351 |
| Vicon Room (6 seqs) | 0.1036 | 0.1148 | **0.0599** |
| all 11 | 0.0950 | 0.1028 | 0.0941 |

**XIVO is 37% better on Machine Hall. OpenVINS is 42% better on Vicon Room.** The
0.0009 m gap in the eleven-sequence mean is two large, systematic, opposite effects
cancelling to within 1%. Reporting only the mean would be true and useless.

Per sequence, `ate_002`:

| sequence | XIVO `acc` | XIVO `fast` | OpenVINS | winner |
| --- | --- | --- | --- | --- |
| MH_01_easy | 0.087 +- 0.007 | 0.080 +- 0.018 | **0.073** +- 0.000 | OV |
| MH_02_easy | 0.052 +- 0.012 | **0.047** +- 0.010 | 0.090 +- 0.011 | XIVO, 1.9x |
| MH_03_medium | **0.099** +- 0.007 | 0.101 +- 0.006 | 0.116 +- 0.003 | XIVO |
| MH_04_difficult | 0.100 +- 0.008 | **0.098** +- 0.009 | 0.207 +- 0.000 | XIVO, 2.1x |
| MH_05_difficult | **0.086** +- 0.012 | 0.115 +- 0.013 | 0.190 +- 0.000 | XIVO, 2.2x |
| V1_01_easy | 0.069 +- 0.004 | 0.074 +- 0.006 | **0.055** +- 0.003 | OV |
| V1_02_medium | 0.071 +- 0.003 | 0.091 +- 0.004 | **0.047** +- 0.002 | OV, 1.5x |
| V1_03_difficult | 0.163 +- 0.009 | 0.157 +- 0.023 | **0.059** +- 0.002 | OV, 2.7x |
| V2_01_easy | **0.050** +- 0.002 | 0.057 +- 0.004 | 0.054 +- 0.004 | XIVO |
| V2_02_medium | 0.091 +- 0.003 | 0.095 +- 0.008 | **0.049** +- 0.002 | OV, 1.9x |
| V2_03_difficult | 0.176 +- 0.018 | 0.215 +- 0.040 | **0.096** +- 0.010 | OV, 1.8x |

The pattern is not noise -- most of these margins are 5-20x the member spread --
and it is not the front end, because it is the same at both XIVO operating points.
What separates the two halves of EuRoC:

* **Machine Hall** is a large, dimly and unevenly lit industrial space, flown
  slowly, with distant structure. Two of the five sequences open with a manoeuvre
  rather than a static hold. OpenVINS' two worst sequences on the entire dataset
  are `MH_04` (0.207) and `MH_05` (0.190), and both are initialisation-limited:
  `MH_04` is the one that needs `--init_dyn_use 1` at all, and it still ends up
  2.1x behind XIVO. XIVO's delayed-initialisation depth handling and its OOS
  (MSCKF-style) path over a 20-pose window are doing real work here -- M5 §6.2
  measured that turning OOS off takes the eleven-sequence mean to 0.219.
* **Vicon Room** is a small, brightly lit room flown fast, with close-range
  features and heavy rotational motion. Feature churn is high and every track is
  short. This is where XIVO loses, and loses consistently: 5 of 6 sequences, by
  1.5-2.7x. `V2_03_difficult` is also where all of XIVO's member spread lives
  (+-0.040 m, against +-0.010 for OpenVINS on the same sequence), which says the
  losses there are gating decisions going different ways rather than a bias.

**RPE-8 tells the opposite story from ATE on exactly these sequences**, which is
the diagnostic. On `V2_03_difficult`, XIVO `acc`'s ATE is 1.8x worse than
OpenVINS' (0.176 vs 0.096) while its RPE-8 position is *equal* (0.075 vs 0.075);
on `V1_03_difficult` XIVO's ATE is 2.7x worse (0.163 vs 0.059) while its RPE-8 is
1.5x worse (0.123 vs 0.083) -- a much smaller factor. A local drift rate that is
competitive alongside an absolute error that is not means the Vicon Room losses are
dominated by **a small number of transient excursions** that ATE integrates and
RPE-8 averages out, not by a uniformly worse motion estimate. Finding and fixing
those excursions is the single highest-value item left on the accuracy axis, and
it is an estimator question, not a configuration one -- M4 already swept the
configuration space around this.

## 5. Which operating point ships, and why

`acc` is better than or equal to `fast` on all five accuracy metrics and costs
2.328 ms/frame more. That is a clean trade with no dominance either way, so
the choice needs stated grounds. **`fast` ships**, on three:

1. **It is the only one of the three configurations that keeps mono `MH_01_easy`
   alive.** M4's config already scored a bad 1.357 +- 0.548 m there; `acc`, which
   adds `KLT.max_level 2` on top of CLAHE, **diverges in 10 of 10 members** (270 m
   to 28 km). `fast`, which has `KLT.max_level 2` but no CLAHE, scores 0.115 m.
   This is a composition effect of exactly the kind M5 §8.2 found in stereo with
   `B0`, and it was invisible in M5 because M5 screened accuracy in stereo only.
   Whatever else is true, shipping a configuration that turns a working sequence
   into a 28 km divergence in a supported mode is not defensible.
2. **It makes the throughput comparison close.** 8.0% behind OpenVINS against
   `acc`'s 29.7%. Since both operating points win and lose the same 3-2 split of
   accuracy metrics, throughput is the axis where they actually differ.
3. **It is what the generator produces**, so the shipped config, the committed
   `cfg/euroc_*.json`, and the documented defaults are one thing rather than three.

What `fast` gives up is the *size* of the position-ATE loss, and that is a real
cost worth stating plainly: `acc` ties `ate_002` with OpenVINS at 0.8 sigma, where
`fast` loses it at 5.1 sigma. Anyone who wants that tie back, and does not need
mono, has it in two flags.


## 6. Mono, as a secondary mode

The brief specifies stereo + IMU for the final evaluation. Mono is reported
because the configuration generator produces both and because it is where the
`acc` failure above showed up. XIVO `fast` vs OpenVINS, n=10 / n=6, all eleven:

| metric | XIVO `fast` | OpenVINS |
| --- | --- | --- |
| `ate_002` (m) | 0.185 | **0.145** |
| ov ATE pos (m) | 0.190 | **0.149** |
| ov ATE ori (deg) | **1.77** | 1.87 |
| RPE8 pos (m) | 0.165 | **0.125** |
| RPE8 ori (deg) | 0.93 | **0.91** |

**OpenVINS wins mono, 4 metrics to 1.** The environment split is the same shape as
stereo but more lopsided: XIVO wins `MH_01`, `MH_02`, `MH_04`, `MH_05` and
`V2_01`, and loses `V1_01` (0.134 vs 0.058), `V1_02` (0.161 vs 0.067) and `V1_03`
(0.325 vs 0.068) by 2-5x. Losing the scale observability of the stereo baseline
amplifies exactly the Vicon Room weakness §3 identifies, which is consistent with
the excursion hypothesis: without a metric baseline, a transient depth error has
nothing to pull it back.

No mono result in this milestone was used to choose a configuration value, only to
reject one (§5).

## 8. What this benchmark does not show

* **Eleven sequences and one dataset.** The environment split in §3 is a strong
  effect but it is two samples of "environment", not a law. Nothing here predicts
  which system wins on a dataset that is neither a machine hall nor a mocap room.
* **The error bars are member spread, not configuration uncertainty** (§1.2).
  Treat any two-configuration difference under ~0.005 m as unresolved.
* **Accuracy and throughput were measured under different protocols** by
  necessity -- the accuracy pass runs 220 processes at once, the timing pass runs
  one pinned process at a time. No number is ever taken from the other pass's
  columns, which is why the `summary.csv` FPS column is never quoted here.
* **OpenVINS' ensemble is not equivalent to XIVO's.** Perturbing `gravity_mag`
  produces genuinely distinct trajectories, but OpenVINS is much less sensitive to
  it than XIVO is to `X.Vsb` (SE 0.0006 vs 0.0016). Its narrower error bars are a
  real property of the estimator on this data, not a measurement artefact -- but
  they are narrower for a different reason than more samples.
* **Timing is single-core by construction.** OpenVINS parallelises differently
  from XIVO, so multi-core throughput is a separate question this protocol
  deliberately excludes.


## 9. Reproduction

All commands from `experiments/openvins`, with the venv on `PATH`:

```sh
export PATH="/home/ubuntu/workspace/auto-slam-engineer/dependencies/venv/bin:$PATH"
```

**Accuracy, both XIVO operating points, n=10, all eleven, both modes** (~50 min on
176 cores; 440 runs):

```sh
CPU_BASE=0 CPU_SPAN=176 ./m6_final_batch.sh          # -> ../results/euroc_m6_final/{fast,acc}
```

**The OpenVINS reference** (M1; already present as `../results/euroc_ov_acc_dyn`):

```sh
./ov_euroc_ens.sh                                     # 6 members, mono + stereo
```

**The head-to-head tables in §2.1, §3 and §4:**

```sh
python3 agg_ensemble.py --mode stereo \
  --arm xivo_acc  ../results/euroc_m6_final/acc \
  --arm xivo_fast ../results/euroc_m6_final/fast \
  --arm openvins  ../results/euroc_ov_acc_dyn/stereo_m*
```

Note the glob must be **unquoted** -- `agg_ensemble.py` takes `--arm NAME DIR`
pairs and expects the shell to have expanded the member directories; quoting it
yields "(not all arms have all sequences)" for every metric instead of an error.
Swap `--mode stereo` for `--mode mono` for §6; `--mode` is mandatory because the
XIVO runner writes both modes into one `summary.csv`.

**Throughput, one core, all eleven** (~40 min per repeat per arm):

```sh
SEQS="MH_01_easy MH_02_easy MH_03_medium MH_04_difficult MH_05_difficult \
V1_01_easy V1_02_medium V1_03_difficult V2_01_easy V2_02_medium V2_03_difficult"
CPU_BASE=0 ./sweep_fps.sh --name fast --seqs "$SEQS" --repeats 1 \
  --out ../results/euroc_m6_fps
CPU_BASE=0 ./sweep_fps.sh --name acc  --seqs "$SEQS" --repeats 2 \
  --out ../results/euroc_m6_fps \
  --patch 'tracker_cfg.histogram_method="CLAHE"' --patch 'tracker_cfg.FAST.threshold=20'
```

**The §2.2 table:**

```sh
python3 report_onecore.py \
  xivo_M4=../results/euroc_fps_base/xivo_r0 \
  xivo_acc=../results/euroc_m6_fps/acc \
  xivo_fast=../results/euroc_m6_fps/fast \
  openvins=../results/euroc_fps_base/ov_r0
```

`report_onecore.py` is new in M6 and exists because `report_fps.py` reads the
`time.txt` that only the XIVO path writes, and so reports a nonzero-exit warning
for every OpenVINS run. Both paths write `stats.txt`, so `report_onecore.py` reads
that instead and handles both directory layouts -- which is what makes the XIVO and
OpenVINS rows of §2.2 the same measurement.

**The n=3 / n=6 / n=10 comparison of §1.2** (the check that the members are the
same runs, not merely the same configuration):

```sh
python3 agg_ensemble.py --mode stereo \
  --arm n3  ../results/euroc_fps_ship \
  --arm n6  ../results/euroc_m6_xivo \
  --arm n10 ../results/euroc_m6_final/fast
```
